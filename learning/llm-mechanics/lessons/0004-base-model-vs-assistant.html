Base model vs assistant

Win: by the end you can explain why a base model continues your text but an assistant answers it, using the same generation loop for both, and say where a "conversation" actually lives in the tokens.

Lesson 3 ended on an observation: GPT-2 never chose end-of-text, even after it had answered a question. It kept writing more Q&A pairs. That's not a GPT-2 bug. It's what every base model does, and the fix doesn't involve changing the loop.

1. Two training stages, one loop

Hugging Face's chat docs put it in one line: "All causal LMs, whether chat-trained or not, continue a sequence of tokens."1 What differs is the data the weights were fitted to:

  • Pretraining fits next-token prediction on a huge corpus of documents. The result is a base model. Given text, it writes the most plausible continuation of that kind of document.1
  • Post-training fine-tunes the base model on data "formatted as a sequence of messages".1 Usually that's supervised fine-tuning (SFT) on example conversations, then a preference stage (RLHF or DPO) that pushes toward replies people rated better.34 The result is an assistant, also called an instruct or chat model.

The pair used below makes this concrete. SmolLM2-360M was pretrained on 4 trillion tokens. SmolLM2-360M-Instruct is the same model after SFT on about 485,000 conversations, then DPO.3 Same architecture, same tokenizer, same loop. Only the weights differ.

ML anchor Think of it as fine-tuning onto a narrow conditional distribution. Pretraining learns P(next token | any web document). Post-training reshapes it toward one document type: a conversation where the assistant's turn is a helpful answer that then ends. The assistant is still continuing a document. It's just a document where the likely continuation is an answer. A prompt that's in-distribution for one model can be out-of-distribution for the other, and run 4 below shows what that looks like.

2. Roles are just tokens

If the model only sees one token sequence, where do "user" and "assistant" go? Into the sequence, as tokens. A chat template renders your list of messages into one string with control tokens that mark each turn.1 This is SmolLM2-Instruct's template applied to a single user message:

<|im_start|>system
You are a helpful AI assistant named SmolLM, trained by Hugging Face<|im_end|>
<|im_start|>user
Summarize in one sentence: Q3 revenue was $4.2M, up 8% from Q2, driven by enterprise renewals.<|im_end|>
<|im_start|>assistant

Three things to notice:

  1. The prompt ends with an empty assistant turn. That's add_generation_prompt=True. Without it, Hugging Face warns, a model may do "something strange, like continuing the user's message instead of replying to it".1 Replying is just the most plausible way to fill an open assistant turn.
  2. There's a system prompt you didn't write. The template adds a default one. What you send isn't always all that's in the context (the same applies to token counts from lesson 3).
  3. <|im_end|> closes every turn. In SFT data, every assistant turn ends with it. That's how an assistant learns to stop.

Formats differ by model family, even for models fine-tuned from the same base.1 OpenAI's open-weight gpt-oss models use the "harmony" format, <|start|>user<|message|>…<|end|>, and OpenAI says gpt-oss "should not be used without using the harmony format, as it will not work correctly".5 With hosted APIs (Claude's Messages API, OpenAI's Responses API) you send a list of messages, and the provider turns them into tokens on its side. OpenAI says so explicitly for gpt-oss served through an API.5 Neither provider asks you to write the format, but some format is there, and it's the reason a "conversation" is really one sequence. Lesson 10 builds on that.

Read the table by column. Stopping splits by weights: only the assistant ever ends a turn (runs 2 and 3). Doing the task needs the right document. The assistant needs its template (3 vs 2), and the base model needs a document whose next line is the answer (5 vs 1). That's how base models were steered before assistants existed: you wrote the start of a document and let the model finish it. A stop sequence (lesson 3's stop_sequence) does the stopping that post-training now does.

4. What post-training buys

InstructGPT (OpenAI, 2022) is the classic evidence. It opens with "Making language models bigger does not inherently make them better at following a user's intent." Labelers preferred outputs from the 1.3B InstructGPT model to those of the 175B GPT-3, "despite having 100x fewer parameters."4 The assistant behaviour you rely on comes from post-training: answering instead of continuing, following the requested format, stopping, tone, refusals, and the persona in that default system prompt.

Where ML intuition misleads It's tempting to treat the assistant as "the base model plus more knowledge", or to think of fine-tuning as how you teach a model your facts. Here the post-training set is tiny next to pretraining (about 485K conversations vs 4T tokens), and what it changed was behaviour. Run 3's summary is correct because the figures were in the context, not because the model knows your revenue. Karpathy's framing in the primary source helps: talking to an assistant is like talking to a simulation of the people who wrote its post-training conversations, built on top of the base model's knowledge of the internet. And that's why a model upgrade can change behaviour even when your prompt hasn't changed. The new model has new post-training.

5. Check yourself

In run 1, why did the base model write Q4 to Q7 figures?

A base model writes the most plausible continuation of the document it's shown. Text that reads like a line of quarterly figures most plausibly continues with more of them. It didn't "decide" to forecast, and the numbers aren't recalled from anywhere.

Run 3 stopped after 22 tokens. What made it stop?

The loop only stops on a special token or a cap. The cap was 60. The assistant picked <|im_end|> as the most likely next token because every SFT reply ends with it. Run 4 had the same template and never stopped.

A teammate sends raw text, with no chat template, to an instruct model running locally. What happens?

Run 2: it ran, stopped, and did the wrong task. Nothing raises. Hugging Face says that with the wrong control tokens, models have "drastically worse performance". Calling the tokenizer directly doesn't apply the template. apply_chat_template does.

What does a hosted messages API do with your system, user, and assistant messages?

Roles are tokens in a single sequence, rendered with the model's chat template on the provider's side. One model reads all of it, and all of it counts toward the context window (lesson 3).

From lesson 3: GPT-2 never chose end-of-text within 60 tokens. In this lesson's terms, why?

GPT-2 has an end-of-text token (ID 50256) and greedy can pick it. But in web text, the end of a document rarely comes right after one answer, so it's rarely the most likely next token. Assistants learn to end turns in post-training.

From lesson 2: the few-shot base run (5) got the summary right. Was it looking anything up?

Same loop as always: score every token, pick one, append. The figures were in the context, and the worked example made a summary the likely next line. The weights didn't change. Steering happens through the input.

Labelers preferred the 1.3B InstructGPT over the 175B GPT-3. What does that show?

Scale buys knowledge and capability. Post-training buys the behaviour people actually rate: following the instruction. The paper's opening line is that bigger "does not inherently" mean better at following intent.

Leading this

Hosted chat APIs serve assistants and handle the format for you, so this goes wrong in two places. First, open-weight or self-hosted models. Ask whether the code calls the model's own chat template, or builds the prompt by hand. A missing or wrong template doesn't raise an error. It quietly makes answers worse (run 2), so it slips past "it runs" checks. Second, model upgrades. A new model version brings new post-training, which can change format, length, and refusals while the prompt stays the same. Treat an upgrade like a dependency bump and rerun your evals before you ship it. That's Stage 3's job, and it's the beginning of why "run it once and check" isn't enough.
