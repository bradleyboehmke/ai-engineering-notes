LLM mechanics · Lesson 1 of 16 · Block A: Text in, text out · ~30 min

Tokens are the unit of everything

Win: by the end you can estimate how many tokens a document is, and say why non-English text, code, and numbers cost more than the rule of thumb suggests.

Your mission starts with estimating what an LLM feature costs before anyone builds it. Every one of those estimates is denominated in a single unit, and it isn't words.

1. The model never sees your text

Before a model reads anything, a tokenizer converts the text into a sequence of integers. Each integer is a token: an ID in a fixed vocabulary of text pieces. Most modern tokenizers use byte pair encoding (BPE), which is lossless and reversible, and keeps common subwords intact.1 Here is a real sentence through OpenAI's o200k_base tokenizer:

The quarterly revenue increased by twelve percent compared to last year.

That's 12 tokens. The model receives [976, 69611, 17981, 11202, …], not the words. Notice the leading spaces: " hello" and "hello" are different tokens with different IDs. A less common word gets split into pieces:

heteroscedasticity
ML anchor The vocabulary is a fixed set of classes. o200k_base has 200,019 of them; the older cl100k_base has 100,277. Generating text is classification over that set, one token at a time. That's lesson 2.

2. Why a builder cares

Every limit and price you'll work with is counted in tokens. That includes how much a model can read (the context window), how much it can write (the output limit), what you pay (priced per million input and output tokens), and how long you wait. Get the token count wrong and every downstream estimate is wrong with it.6

3. The rule of thumb, and where it breaks

For English, OpenAI gives the standard rule: 1 token ≈ 4 characters ≈ ¾ of a word, so 100 tokens ≈ 75 words. It also says plainly that this is an approximation, and that other languages behave differently.3

Measured cases show where it holds and where it fails:

The multilingual gap is well documented. Across 17 tokenizers, the same text translated into different languages varied in length by up to 15×. That affects cost, latency, and how much fits in context.4 Tokens also explain some well-known model failures, such as trouble spelling, reversing strings, and simple arithmetic. The model sees heter+os+…, never the individual letters.2

4. Every provider counts differently

The two OpenAI tokenizers above disagree on the same text. Providers differ too. Anthropic's documented way to count Claude tokens is its token-counting API endpoint, which takes a full message and returns an estimate of the input tokens.5 So a tiktoken count is exact for the OpenAI model it matches, and only an approximation for anyone else's model.

A plain-text count also leaves out request overhead: message structure, tool definitions, images, and files all add tokens.3 That's lesson 10.

5. Check yourself

Answer from memory, without scrolling up. Retrieval is what makes this stick.

A teammate budgets a 3,000-word English report as 3,000 tokens. What's the better estimate?

100 tokens ≈ 75 words, so 3,000 words ≈ 4,000 tokens. 12,000 comes from applying the 4-characters rule to words instead of characters.

Why does a model struggle to count the letters in "heteroscedasticity"?

The input is five tokens (heter, os, ced, astic, ity). The letters were never presented as separate units.

You serve the same feature in English and Hindi. Which is most likely true?

The same meaning took 20 to 66 tokens in Hindi versus 12 in English. Tokenizers are trained mostly on English-heavy data.

You count a prompt with tiktoken. How should you use that number for a Claude bill?

tiktoken matches OpenAI's tokenizers. For Claude, use Anthropic's token-counting endpoint, which is itself an estimate.

Which of these is not measured in tokens?

Parameters are model weights. Context, output limits, and price are all counted in tokens.

6. Experiment: count your own documents (~10 min)

Do this
  1. Pick three public documents of different kinds: a page of prose (an article or README), a code file, and something with numbers or tables. Optionally add a fourth in another language. Use no work documents.
  2. From learning/llm-mechanics/, create a virtual environment (already gitignored): 
    python3 -m venv .venv && .venv/bin/pip install tiktoken
    Save this as experiments/count.py: 
    import sys, tiktoken
enc = tiktoken.get_encoding("o200k_base")
for path in sys.argv[1:]:
    text = open(path, encoding="utf-8").read()
    n = len(enc.encode(text))
    print(f"{path}: {n} tokens, {len(text)/n:.1f} chars/token, "
          f"{len(text.split())/n:.2f} words/token")
    Then run .venv/bin/python experiments/count.py doc1 doc2 doc3.
  3. Before you run it, write down your guess for each document using the rule of thumb. Then compare.
  4. Note which document beat the rule and which broke it, and why. That observation is the start of your dictionary entry.

Leading this

When a teammate's design doc gives sizes in pages or words, ask for tokens. If the product is multilingual, ask for token counts per language, because the budget for a Hindi user isn't the budget for an English one. "Words ÷ 0.75" is fine for a first estimate of English prose. Anything with code, tables, or numbers needs a measured count.
