Context window and output limits

Win: by the end you can budget a request (input + output must fit in the context window, and output can't exceed the max output), and read the stop reason to tell a finished answer from a cut-off one.

The generation loop from lesson 2 ends one of two ways: the model emits an end-of-text token, or something stops it. This lesson covers the things that stop it, and why your request has a fixed amount of space in the first place.

1. The window is the loop's working space

Anthropic defines the context window as "all the text a language model can reference when generating a response, including the response itself", and contrasts it with the training data: it's a "working memory".1 Everything you send counts toward it: system prompt, messages, tool definitions, images, documents. So does everything the model generates, including thinking.1

Why does the response count? Look at the loop again: tokens.append(next). Every output token becomes input for the next step. By the last token of a reply, the model is reading the prompt plus everything it has written so far. Input and output share one sequence, so they share one limit.

ML anchor For GPT-2, the window is literally a tensor shape. Its learned position embeddings are a 1,024 × 768 table, one row per position. Token 1,025 has no row, and the forward pass fails with IndexError: index out of range (measured below). Newer models encode position differently, but the window is still a fixed property of the model as built and served, and providers publish it per model.

2. Two limits, three numbers

Every request has to satisfy two constraints:

input_tokens + max_tokens  ≤  context window     # the shared space
               max_tokens  ≤  max output         # the model's ceiling on one reply

That's three numbers. Two of them belong to the model and one belongs to you:

  • Context window (model): total tokens in play, input plus output.
  • Max output (model): the most a single reply can generate, however much room is left.
  • max_tokens (you): the cap you set on this reply. It's a required parameter on Claude's API.

Two practical notes. Max output (128K) is much smaller than the window (1M), so a request can have plenty of room and still be capped. And thinking tokens are "a subset of your max_tokens" and are billed as output.1 OpenAI says the same about reasoning tokens, and warns that a capped response "could incur costs for input and reasoning tokens without receiving a visible response".5 Lesson 5 covers reasoning models.

The three runs map onto the three outcomes a production API gives you:

  1. Your cap hit first. The reply is truncated. Run 1 stopped exactly where a list was about to continue. The model didn't wrap up, because it wasn't pacing itself against the cap. Anthropic calls max_tokens "the enforced limit" that "truncates the response". It offers a separate, advisory task budget when you want the model to pace itself and finish gracefully.6
  2. The window filled first. On Claude 4.5 and newer models, a request where input + max_tokens exceeds the window is accepted. If generation reaches the window, it stops with stop_reason: "model_context_window_exceeded". Earlier models reject the request with a validation error instead.1
  3. The input alone doesn't fit. The API returns HTTP 400, "prompt is too long", on every model.1 Nothing is generated. Nothing is silently dropped either, unless you turn on a feature like compaction.

One more observation: in my extra runs, GPT-2 never chose end-of-text within 60 tokens, even after it had answered a one-line question. It kept writing more Q&A pairs. A base model has no notion of "done". Lesson 4 explains how assistants learn to stop.

Where ML intuition misleads In classical sequence models, "max sequence length" is an input constraint. Here the output uses the same budget, so a long prompt leaves less room for the answer (run 2). The bigger trap is assuming a prompt that fits will work. Anthropic's own definition warns that "more context isn't automatically better": accuracy and recall degrade as the token count grows (context rot).1 Fitting is necessary. It isn't sufficient. Lesson 15 measures this.

4. Truncation is silent: read the stop reason

A truncated response is not an error. You get HTTP 200, a normal-looking body, and half an answer. If the answer is JSON, you might get half an object. The only signal is a field you have to check:

Claude stop_reasonMeaningWhat your code does
end_turnThe model finished on its ownUse the response
max_tokensYour cap hit firstRaise max_tokens, or continue the response
model_context_window_exceededThe window filled firstTreat it as truncated
 The three stop reasons this lesson covers, from Anthropic's stop-reason docs.2 The others (tool_use, stop_sequence, pause_turn, refusal) come up in Stage 2.

A truncated reply still costs money. usage.output_tokens reports every token that was generated, and that's what you're billed for (lesson 12). One practical detail: Claude's Python SDK requires streaming for max_tokens above about 21K, to avoid HTTP timeouts.2

5. Budget a request

Here's a mission-shaped example. An analytics assistant answers questions over ten years of quarterly reports: 40 reports of about 12,000 words each, plus a 3,000-token system prompt and table schema. Anthropic's docs put 1M tokens at about 555K words on Claude's current tokenizer.3 That's about 1.8 tokens per word, so 480,000 words is roughly 865,000 tokens.

Do this (3 min)
  1. Each extra report adds about 21,600 tokens. Before touching the widget, work out how many reports you can include and still keep the full 16,000 tokens of output room. Then check it.
  2. Add three more years (12 reports). What happens, and on which line of section 3 does it land?
  3. Switch to Claude Haiku 4.5 (a 200K model). How many reports fit now?
Answers

(1) (1,000,000 − 3,000 − 16,000) ÷ 21,622 ≈ 45.4, so 45 reports. (2) 52 reports ≈ 1,127,000 input tokens: rejected with a 400 before generation, outcome 3. The request worked for years and then broke the quarter the archive grew. (3) (200,000 − 3,000 − 16,000) ÷ 21,622 ≈ 8.4, so 8 reports. Note the rate is an estimate: count real tokens with the provider's counting endpoint before you rely on it.7

6. Check yourself

On a 1M-window Claude model, a request has 990,000 input tokens and max_tokens = 20,000. What happens?

The input fits, so on Claude 4.5 and newer the request is accepted. Only 10,000 tokens of room remain. If generation gets there, the stop reason is model_context_window_exceeded. Earlier models reject it. Nothing is dropped or summarized unless you turn on compaction.

Your app gets HTTP 200 with stop_reason "max_tokens". What do you have?

max_tokens is an enforced cut, not a length hint. The reply stops mid-thought (GPT-2 stopped right before step 2), and usage.output_tokens still counts every generated token.

From lesson 2: why do input and output share one context window?

The loop appends each chosen token and runs again. By the final step, the sequence is the prompt plus everything generated, and all of it has to fit.

GPT-2 raised IndexError on a 1,025-token input. Why at exactly that length?

GPT-2 learns one embedding per position, in a 1,024 × 768 table. Position 1,025 has no row to look up. Its vocabulary is 50,257 tokens, which is a separate number.

A reasoning model returns empty visible text with its output cap hit. Most likely cause?

Thinking tokens count toward max_tokens / max_output_tokens on both providers. A tight cap can be used up before any visible text. OpenAI suggests reserving at least 25,000 tokens for reasoning and output when you start out.

From lesson 1: Claude's current tokenizer fits about 2.5M characters in 1M tokens. A 400,000-character document is about…

400,000 ÷ 2.5 = 160,000. The "4 characters per token" rule gives 100,000, an undercount of 60,000, which is the same gap you measured in lesson 1 (2.7–3.7 chars/token). On a 200K-window model, that difference decides whether the document fits.

Leading this

Two review questions catch most mistakes here. First: what stops this input from growing? Conversation history, retrieved documents, and "include all the reports" all grow over time. A design that fits today can fail with a 400 the quarter the data doubles. Look for a bound, whether that's a cap, a window of recent items, retrieval, or compaction. Second: does the code check the stop reason? A max_tokens cut returns 200 OK, so without that check, truncated JSON or a half-finished summary goes downstream unnoticed. Ask how max_tokens was chosen, and what the code does when it's hit.
